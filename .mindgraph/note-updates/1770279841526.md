### ⚠️ 修正 2：笔记解释了"为什么不交错"，但没解释"为什么大写在前"

笔记里写的是「单个 P 的时间片足够跑完一个 goroutine，**没有交错**」——
这句话解释了 *为什么没有交错*，但**没有解释为什么大写整块在前**。
后者跟时间片毫无关系，是 **runnext VIP 槽的 LIFO 行为**。补充如下。

**Go runtime 里每执行一次 `go func(){}`，走的是：**

```
newproc → runqput(pp, g, next=true)
```

`next=true` 表示新 goroutine 进 `pp.runnext` 这个**单槽 VIP 位**；
**槽里已经有人时，被挤下来的那个塞进本地环形队列的尾部**。
调度器取任务时（`runqget`）**先取 runnext，再从环形队列头部取**。

所以 `listing01.go` 里大写是**第二个** `go func()`，它占了 VIP 槽 → **先跑**；
小写被挤到队列尾部 → 随后跑。**这跟时间片一点关系都没有。**

> 实测反证：把两个 `go` 语句的顺序对调，输出顺序**整个翻转**（小写变先跑）。
> 如果是 FIFO 抢队列，对调创建顺序不会产生这种效果。

### 补充 3：三个机制的源码出处（go1.27.4，`$GOROOT/src/runtime/`）

| 机制 | 出处 |
|---|---|
| 新 G 进 VIP 槽，被挤下的进队列尾部 | `proc.go` `runqput()`：`// Kick the old runnext out to the regular run queue.` |
| 队列是 **256 格**环形数组 | `runtime2.go`：`runq [256]guintptr` |
| 取任务先 VIP 后队头（FIFO） | `proc.go` `runqget()`：先 CAS `pp.runnext`，再 `pp.runq[h%256]` 按 h 递增取 |
| 时间片 **10ms** | `proc.go`：`const forcePreemptNS = 10 * 1000 * 1000 // 10ms` |
| 被抢占的 G 进**全局**队列 | `proc.go` `gopreempt_m()` → `goschedImpl(gp, true)` → `globrunqput(gp)` |
| **本地队列优先于全局队列** | `proc.go` `findRunnable()`：`// local runq` 的 `runqget(pp)` 在 `// global runq` 的 `globrunqgetbatch()` 之前 |
| **`-race` 下调度器随机化** | `proc.go`：`const randomizeScheduler = raceenabled` + `runqput()` 里 `randn(2) == 0` |

### 补充 4：`-race` 不只是"查竞态"，它还会**打乱调度顺序**（重要，最容易踩）

```go
// runtime/proc.go
const randomizeScheduler = raceenabled

func runqput(pp *p, gp *g, next bool) {
	...
	if randomizeScheduler && next && randn(2) == 0 {
		next = false        // ← 50% 概率放弃 runnext，直接进环形队列
	}
}
```

竞态检测器构建下 `raceenabled == true`，`runqput` 有 **50% 概率不走 runnext**，
**VIP 槽待遇没了，goroutine 顺序也就随机了**。

实测（`listing01.go`）：

- 普通构建：5 次全是**大写先打**（runnext VIP 槽生效）
- `go run -race listing01.go`：5 次全是**小写先打**（顺序翻转）

> 这条直接推翻了"顺序是固定的"这种直觉。**同一个源码，只加个 `-race` 编译标志，
> goroutine 执行顺序就变了。**

### 补充 5：新增 `listing01_five.go` —— 把三个机制一次看全

起 **5 个匿名 goroutine**，创建顺序 G1→G2→G3→G4→G5，每个打印截然不同的内容，
每行带 `[Gx +12.345ms]` 前缀（身份 + 相对启动的毫秒数），main 在每个 `go` 后打印
`main: created Gx` 以便对照"创建顺序 vs 执行顺序"。

| G | 打印内容 | 工作量 | 观察点 |
|---|---|---|---|
| G1 | 大写字母表 ×3 轮 | 极轻（≈0.01ms） | runnext 整块输出 |
| G2 | `01`–`50`，每 10 个一行 | 中等（≈0.05ms） | 环形队列第 2 位 |
| G3 | **筛 2000 万以内素数**，计算期间一个字符不打，只打 `start:` / `done:` | **极重，≈140ms**（14 个时间片） | **被抢占的现场** |
| G4 | `#=+*` 图案 40 行 | 中等（≈0.1ms） | 从被抢占的 G3 手里抢走 CPU 的那个 |
| G5 | 中文句子 + emoji，10 行 | 中等（≈0.03ms） | **最后创建 → runnext VIP 槽** |

G3 选素数筛是刻意的：纯 CPU、结果确定（1,270,607 个素数）、时间可控。
本机实测耗时曲线：2M→6.7ms，5M→19.4ms，10M→46.5ms，**20M→137.1ms**，40M→339.2ms。

**三次运行的实测结论：**

**① `GOMAXPROCS=1`（最干净，三个机制全可见）**

```
main: created G1 / G2 / G3 / G4 / G5      ← 创建顺序
[G5 + 0.063ms] 第 1 行…                    ← G5 先跑（LIFO：VIP 槽）
[G1 + 0.086ms] ABCDEFG…                    ← G1 第二（FIFO：队头）
[G2 + 0.093ms] 01 … 50                     ← G2 第三
[G3 + 0.141ms]  start: sieving…            ← G3 第四
        ← 这里空了一整段（约 15ms），一个字符都没打
[G4 + 15.367ms] 1  #=+*…                   ← G4 抢走了 CPU
[G4 + 15.449ms] 40 #=+*…                   ← G4 一口气打完 40 行
[G3 + 154.336ms]  done: primes = 1270607    ← G3 最后才报数
```

**执行顺序 G5 → G1 → G2 → G3 → G4**，与假设逐条对上：
G5 抢到 VIP 槽（G1 被挤下来落到环形队列**队头**，所以第二个跑）。

**铁证在 G3 和 G4 的关系上**：G3 的**创建顺序在 G4 之前**、**启动也早于 G4**
（0.141ms < 15.367ms），可 G3 的 `done:` 行却排在 G4 全部 40 行**之后**
—— 只可能是 G3 中途被抢走过。空白约 15ms 而非正好 10ms，是因为抢占是**异步**的：
sysmon 轮询 + 发 `SIGURG` + 目标 G 要跑到安全点才能被切走，开销叠加。

**② 普通构建（默认 8 个 P）**

- G5 **仍然第一个**（runnext 是 **per-P** 的，main 那个 P 的 VIP 槽别的 P 抢不走）；
- 但 G3/G4/G2/G1 的首行分别落在 0.143 / 0.182 / 0.151 / 0.229ms，**挤在 0.09ms 窗口内**
  → 它们**同时在不同 P 上并行执行**，所以**环形队列的 FIFO 顺序在多 P 下根本观察不到**；
- G2 身上能看到抢占：`[G2 + 0.151ms] 01` 之后**隔了 0.47ms** 才打 `02`。

**③ `go run -race`（8 个 P）**

- **第一个跑的是 G4，G5 垫底** —— `randomizeScheduler` 把 runnext 随机废掉了；
- G3 耗时从普通构建的 **142.673ms** 涨到 **1131.424ms**（**慢约 8 倍**）
  —— race detector 给每次内存访问插桩，G3 那 20MB `[]bool` 被访问了几千万次；
- 仍是 **0 条 `WARNING: DATA RACE`**（五个 G 之间没有共享内存，符合预期）。

### 补充 6：Listing 6.7 的交错次数是**每次跑都不一样**的

笔记写「5 次里 2 次出现逐字符交错」——方向对，但这个数字本身就是随机的。
本轮补测 **8 次，其中 3 次出现交错**（第 2、5、8 次），5 次是干净的。

其中一次的开头是 `aABCDEFGHIJ...ABCbcdefghij...` —— **小写的 `a` 打在了最前面**。
这在非 `-race` 构建下出现，是因为 GOMAXPROCS=2 时**第二个 P 会去窃取（steal）第一个 P 的任务**，
而窃取是从队列**尾部**取，第一个创建的 goroutine 有机会被窃取者先捡走。
**所以连"第一个跑的是谁"在多 P 下都不固定。**

### 一句话补充结论

> **`go` 语句只管入队不管顺序：新建 G 先进 P 的 runnext VIP 槽（LIFO → 最后创建的最先跑），
> 被挤下去的按创建顺序（FIFO）排在本地 256 格环形队列里；
> 单个 G 超过 10ms 时间片会被抢占并推到队尾，让位给排在它前面的 G。
> 这一切都是实现细节 —— 换台机器、换个 Go 版本、加个 `-race`、把 GOMAXPROCS 从 1 改成 2，
> 顺序就变。唯一能依赖的只有 `WaitGroup`（都跑完了）和 `channel`（数据同步了）。**
